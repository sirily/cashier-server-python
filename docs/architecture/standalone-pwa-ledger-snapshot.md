# Проект: автономный `main.bean` для Cashier PWA без потери семантики исходной книги

- Статус: PR #6 был смержен, но production QA выявил regression; документ ниже фиксирует обязательный follow-up перед новым merge
- Область изменений: `cashier-server-python`
- Целевой endpoint: `GET /infrastructure?file_path=main.bean`
- Потребитель результата: Cashier PWA через `@rustledger/wasm@0.14.1`
- Процессное ограничение: новые PR по этому направлению нельзя мержить без явного разрешения владельца репозитория

## 1. Задача

Cashier PWA должен получить от сервера один автономный файл `main.bean`, который:

- не содержит `include` и не требует других файлов;
- не содержит Python `plugin` и не требует Python в браузере;
- включает результат выполнения серверных Python-плагинов;
- сохраняет смысл исходных пользовательских записей, в частности точные валютные операции с `@@`;
- разбирается тем же `@rustledger/wasm@0.14.1`, который использует PWA, без ошибок;
- остаётся read-only снимком серверной книги для Stage 1: локальные транзакции Cashier продолжают храниться отдельно в `cashier.bean`.

## 2. Подтверждённая причина текущей ошибки

После развёртывания PR #5 сервер успешно загружает рабочую книгу и отдаёт материализованный корневой файл, но PWA получает 25 ошибок баланса на валютных переводах.

Проверкой на отдельной записи установлена точная последовательность:

1. В исходном файле операция содержит total price (`@@`).
2. Уже `beancount.parser.parser.parse_file()` преобразует `@@` во внутренний объект с вычисленной ценой за единицу (`@`).
3. `beancount.loader.load_file()` возвращает тот же нормализованный объект.
4. Текущий сервер печатает весь результат через `EntryPrinter(dcontext=options_map["dcontext"])`.
5. `EntryPrinter` округляет вычисленную цену за единицу до обычной точности валюты.
6. Округлённая цена перестаёт воспроизводить точную исходную сумму; RustLedger правильно сообщает ошибку баланса.

Отдельной проверкой установлено:

- текущий `@rustledger/wasm@0.14.1` принимает исходную запись с `@@` без ошибок;
- восстановление исходных `@@` в анализируемой копии production snapshot уменьшает число ошибок RustLedger с `25` до `0`;
- добавление tolerances может скрыть часть ошибок, но не восстанавливает утраченную семантику.

Следовательно, неисправность находится в способе серверной сборки файла, а не в движке разбора PWA.

## 3. Главное архитектурное правило

Сервер не должен считать результат `parse -> plugin execution -> EntryPrinter` обратимым представлением исходной книги.

Исходный текст является единственным надёжным источником написанной пользователем семантики: `@@`/`@`, точность чисел и иные различия исходной записи. Объекты Beancount после разбора являются источником результата вычислений и плагинов, но не источником для дословного восстановления исходных директив.

Новый сборщик снимка должен работать как компилятор с сохранением происхождения записи:

- для неизменённых исходных директив брать исходный текст;
- для удалённых плагином директив ничего не выводить;
- для созданных плагином директив выводить материализованный результат;
- для изменённых плагином исходных директив выводить результат изменения, но сохранять исходные смысловые фрагменты (например `@@`), если плагин их не изменил.

## 4. Что сервер будет отдавать

Контракт HTTP не меняется:

```json
{ "content": "...автономный main.bean..." }
```

Меняется смысл содержимого корневого файла:

- это не повторная печать всех записей из `loader.load_file()`;
- это специально собранный автономный снимок книги для офлайн-исполнения в PWA.

Для не-root запросов и glob-запросов существующий контракт можно сохранять, пока PWA в режиме автономного корня не нуждается в этих файлах для полного разбора.

## 5. Составные части решения

### 5.1. Индекс исходных файлов

Компонент `SourceLedgerIndex` читает root-файл и все включённые файлы в пределах разрешённой директории книги.

Он должен хранить:

- относительный путь файла;
- исходный текст;
- блоки директив с диапазонами строк;
- порядок включения файлов;
- расположение `include`, `plugin` и исполняемых служебных директив;
- исходные фрагменты posting-ов, включая `@` и `@@`.

Для хранения текста недостаточно объектов, полученных из Beancount parser: исходная форма `@@` в них уже отсутствует. Нужен слой, сохраняющий текстовые блоки до вызова Beancount loader. Первоначально это может быть безопасный сканер директивных блоков с привязкой к `filename`/`lineno`; если его недостаточно для поддерживаемого синтаксиса, потребуется полноценное представление исходного текста с позициями.

### 5.1.1. Production regression после PR #6

Production root `main.bean` может начинаться с prose/org-style заголовков, например:

```beancount
* Beancount configuration
; Note that plugin order is important

option "plugin_processing_mode" "raw"
```

Такие строки не являются бухгалтерскими entries и не должны приводить к выдаче потенциально искажённого снимка. Source-preserving builder обязан обрабатывать их явно:

- regression test должен начинаться именно с org-heading на первой строке root file;
- endpoint `/infrastructure?file_path=main.bean` должен возвращать `200`, а не `422 Unsupported non-entry source directive at main.bean:1`;
- итоговый snapshot должен оставаться валидным для `@rustledger/wasm@0.14.1`;
- если RustLedger не принимает такие prose строки как есть, builder должен преобразовать их в Beancount comments, сохранив текст и не меняя бухгалтерскую семантику;
- это правило должно войти в clean Docker acceptance, чтобы fixture покрывал production-shape root preamble, а не только `@@`-семантику.

### 5.2. Выполнение книги на сервере

Компонент `MaterializedLedgerRun` выполняет текущую серверную обязанность:

- вызывает Python Beancount loader на исходном root-файле;
- выполняет все настроенные Python-плагины;
- прекращает выдачу снимка при ошибках загрузки или плагинов;
- получает итоговые entries и служебные metadata о происхождении.

Он не занимается окончательной печатью всей книги.

### 5.3. Классификация результата

Компонент `DirectiveReconciler` сопоставляет исходные директивы и результат выполнения плагинов.

Для каждой итоговой записи определяется один из режимов:

| Режим | Что произошло | Что выводить |
|---|---|---|
| `retained` | Исходная директива семантически не изменена | Исходный текст целиком |
| `removed` | Исходная директива поглощена или удалена обработкой | Ничего |
| `generated` | Запись создана плагином/материализацией | Печатать материализованную запись |
| `transformed` | Плагин изменил исходную директиву | Печатать изменённый результат с сохранением применимых исходных смысловых фрагментов |
| `unsupported` | Невозможно доказать корректное преобразование | Прервать сборку с диагностикой, не отдавать потенциально неверную книгу |

Сопоставление должно использовать происхождение (`filename`, `lineno`, тип записи), а для преобразованных записей — правила конкретного плагина. Недопустимо угадывать соответствие только по дате, счёту или сумме.

#### 5.3.1. Две границы для встроенного booking (`{}`)

Некоторые исходные директивы меняются ещё до Python plugins: Beancount core booking разрешает пустой FIFO cost spec (`{}`) в выбранный concrete lot. Это не plugin transformation и при неизменённом последующем результате допустимо выводить исходным текстом, чтобы PWA самостоятельно выполнила то же booking.

Reconciler поэтому сравнивает три представления:

1. `raw source` из `SourceLedgerIndex`;
2. `booked baseline`, полученный стандартными parse + `booking.book()` без выполнения transformations/plugins;
3. `materialized final`, полученный полным `loader.load_file()` с plugins.

Запись с `{}` может быть `retained` только если `raw source -> booked baseline` отличается исключительно допустимым core-booking completion **и** `booked baseline == materialized final` по пользовательской семантике. Если plugin после booking меняет выбранный cost, posting или транзакцию, исходный `{}` не может скрыть эту мутацию: применяется обычная transformed/fail-closed policy.

### 5.4. Реестр правил плагинов

Нельзя считать, что все плагины только добавляют записи. Production workspace использует плагины, которые могут изменять, группировать, фильтровать или заменять исходные директивы.

Нужен явный `PluginExportPolicyRegistry`. Для каждого поддерживаемого в production плагина в нём фиксируется:

- класс поведения: добавляет, удаляет, заменяет, изменяет, потребляет operational directive;
- каким образом устанавливается происхождение результата;
- какие исходные директивы не должны попасть в снимок;
- какие фрагменты исходной записи допустимо сохранить в преобразованном результате;
- какие регрессионные тесты доказывают корректность правила.

Начальный перечень для аудита, соответствующий рабочей среды и тестового набора:

| Плагин | Ожидаемый предмет аудита |
|---|---|
| `beancount.ops.documents` | Добавление директив документов |
| `beancount.ops.pad`, `beancount.ops.balance` | Поглощение `pad` и создание/проверка padding результата |
| `beancount.plugins.implicit_prices` | Добавление цен из postings |
| `beancount_lazy_plugins.valuation` | Генерация valuation-related записей/metadata |
| `beancount_lazy_plugins.generate_inverse_prices` | Генерация цен |
| `beancount_lazy_plugins.generate_base_ccy_prices` | Генерация цен |
| `beancount_lazy_plugins.group_pad_transactions` | Замена/группировка операций выравнивания |
| `beancount_lazy_plugins.filter_map` | Изменение transactions/metadata/payee/narration/tags |
| `beancount_lazy_plugins.auto_accounts` | Генерация account directives |
| `beancount_share.share` | Изменение отмеченных transactions и/или создание связанных entries |
| `beancount_reds_plugins.effective_date.effective_date` | Замена/расщепление transactions по effective date |
| `beancount_interpolate.recur`, `beancount_interpolate.split` | Генерация либо преобразование transactions |

До окончания аудита плагин с неописанным поведением должен приводить к отказу формирования автономного снимка, а не к тихой выдаче потенциально неверной книги.

### 5.5. Сборка автономного файла

Компонент `StandaloneSnapshotBuilder` формирует итоговый текст в детерминированном порядке.

Он должен:

1. Собрать директивы всех исходных включённых файлов в одну книгу.
2. Не выводить исходные `include`, потому что их содержимое уже включено в результат.
3. Не выводить исходные `plugin`, потому что PWA не исполняет Python-код.
4. Не выводить исполненные служебные директивы, например `pad`, если результат уже материализован сервером.
5. Для `retained` вывести исходные блоки без parse/print round-trip.
6. Для `generated` вывести результат через специализированный безопасный printer.
7. Для `transformed` вывести подтверждённое правилом плагина представление результата.
8. Добавить стабильные разделители/комментарии о происхождении только если они не меняют разбор и полезны для диагностики.

### 5.6. Вывод созданных и преобразованных записей

Для записей, которым нет дословного исходного аналога, нужен `PwaMaterializedEntryPrinter`.

Его обязанности:

- выдавать синтаксис, принимаемый RustLedger;
- канонизировать недопустимые текстовые metadata keys/values так, как уже требуется для PWA;
- никогда не применять обычное display-округление к price/cost, если оно изменяет баланс;
- проверять, что напечатанная запись сохраняет вес и баланс материализованной записи;
- при невозможности безопасно вывести запись завершать сборку ошибкой.

Он не должен использоваться для массовой повторной печати неизменённых пользовательских директив.

### 5.7. Сохранение семантики в изменённых transactions

Плагины вроде `filter_map`, `share` или `effective_date` могут изменить исходную transaction, поэтому её нельзя всегда вывести целиком из исходного текста.

Для `transformed` режима правило такое:

- если posting с исходным `@@` перешёл в итоговую transaction без изменения account, units и total-price смысла, сборщик должен перенести его исходную обозначение цены `@@` в вывод преобразованной transaction;
- если плагин действительно изменил сумму, валюту или смысл price/cost, исходная price-аннотация не переносится; новое представление должно быть сформировано без потери точности и проверено RustLedger;
- если это нельзя доказать, снимок не выдаётся.

Таким образом архитектура не ограничивается только «исходный текст плюс новые записи» и корректно предусматривает плагины, меняющие пользовательские операции.

## 6. Поведение при ошибках

Сборщик должен быть fail-closed.

Endpoint возвращает ошибку и подробную серверную диагностику, если:

- Beancount loader или plugin execution вернули ошибки;
- обнаружен включённый файл вне разрешённого root;
- присутствует плагин рабочей книги без зарегистрированного export policy;
- итоговую запись нельзя надёжно сопоставить с source/generated/transformed режимом;
- безопасный вывод преобразованной/generated записи не доказан;
- финальный снимок не проходит валидацию RustLedger в тестах.

Нельзя выдавать PWA снимок, про который сервер не способен обосновать сохранение бухгалтерской семантики.

## 7. Не входят в решение

Это изменение не должно:

- добавлять запись операций обратно на сервер транзакций;
- менять хранение локальных операций PWA в `cashier.bean`;
- переносить выполнение Python-плагинов в браузер;
- заменять `@rustledger/wasm` без отдельной причины;
- лечить потерю точности увеличением tolerances;
- вводить новый внешний API-контракт вместо существующего `{ "content": "..." }`.

## 8. Критерии готовности

Решение готово к развёртыванию только если выполнены все условия:

- автономный `main.bean` не содержит `include` и директивы Python-плагинов;
- исходная запись `@@` в неизменённых либо допустимо преобразованных transactions сохраняет точный смысл;
- исходный настоящий `@` не заменяется на `@@`;
- материализованный результат `pad` присутствует, а исполненный `pad` не исполняется повторно;
- metadata, созданные плагинами, остаются читаемыми PWA;
- для каждого используемого рабочего плагина существует документированное правило и тест;
- Docker image, собранный из PR, выдаёт снимок через HTTP endpoint;
- этот снимок разбирается `@rustledger/wasm@0.14.1` с `0` errors на основанными на рабочей книге fixture;
- после развёртывания `/sync` в рабочей среде показывает `Full ledger parsed ✓` и `Parse errors: 0`.
