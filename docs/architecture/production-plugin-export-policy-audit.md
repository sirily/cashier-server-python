# Аудит правил вывода плагинов рабочей книги в автономный `main.bean`

- Статус: обязательная рабочая матрица перед реализацией сборщика
- Назначение: не допустить ошибочное предположение, что все плагины только добавляют новые записи

## 1. Зачем нужен этот аудит

Новый автономный снимок сохраняет исходный текст там, где исходная директива не изменилась. Это безопасно только после ответа на вопрос: что именно сделал каждый Python-плагин с исходной директивой?

Если плагин изменил пользовательскую transaction, нельзя одновременно:

- оставить её исходный текст;
- добавить изменённый результат как новую запись.

Это даст двойной или неверный учёт. Поэтому каждый активный plugin должен получить явное правило вывода и тест.

## 2. Категории правил

| Категория | Значение | Разрешённый вывод |
|---|---|---|
| `additive` | Только создаёт новые записи, исходные остаются прежними | Исходные блоки сохранить; новые записи напечатать |
| `consumer` | Поглощает operational directive и создаёт итоговый результат | Исходную исполняемую directive исключить; итог вывести |
| `transformer` | Изменяет исходную пользовательскую директиву | Исходный блок не выводить; вывести подтверждённое преобразование с сохранением допустимого исходного смысла |
| `filter` | Удаляет часть исходных directives | Удалённые блоки не выводить только при доказанном правиле |
| `unsupported` | Поведение ещё не доказано | Автономный снимок не формировать |

## 3. Исходный перечень плагины рабочей книги

Перечень взят из тестовой книги, повторяющей рабочую конфигурацию, и из ранее обнаруженных зависимостей среды выполнения. Таблица ниже — план аудита, а не утверждение о полностью доказанном поведении каждого плагина.

## 4. Уже подтверждённые сведения из исходников и QA

### `beancount_lazy_plugins.filter_map`

Исходник плагина прямо описывает операции над проводками:

- добавление меток;
- добавление метаданных;
- установка получателя;
- установка описания.

Поэтому этот plugin нельзя обработать как «оставить source transaction и добавить созданного результата»: для затронутых операций требуется режим `transformed` («изменена»).

### `beancount_lazy_plugins.group_pad_transactions`

Исходник собирает созданные операции выравнивания и объединяет группы в одну transaction. Значит, этот plugin работает с уже созданными результатами `pad` и требует согласованной политики с `beancount.ops.pad`/`balance`.

### `beancount_share.share`

Исходник формирует `new_entries` через обработку отмеченных операций. До тестового сравнения input/output он рассматривается как преобразующий plugin; простое сохранение исходной отмеченной операции небезопасно.

### `beancount_reds_plugins.effective_date.effective_date`

Исходник создаёт новые записи на основе операции и её проводок с `effective_date`, меняя дату и postings. Это преобразование, а не только добавление независимой записи.

### `@@` и стандартный Beancount parser

Независимо от plugin policy, проверка показала: исходная price-форма `@@` отсутствует уже после Python Beancount parser. Поэтому любое правило для `transformed` transaction, способной содержать исходную запись `@@`, должно иметь доступ к исходному текстовому posting и явно сохранять total-price смысл, если преобразование его не меняет.

## 5. Шаблон теста для одного plugin policy

Для каждого плагина нужно создать небольшой ledger, где есть:

- минимально необходимая конфигурация плагина;
- одна незатронутая исходная запись;
- одна затронутая исходная запись;
- при необходимости проводка валютной конверсии с округлением с `@@` в затронутой transaction;
- ожидаемые generated/removed/transformed записи.

Тест должен подтвердить:

1. Какой исходный блок соответствует итоговой записи.
2. Исчезает ли исходный блок из материализованных записей.
3. Создаются ли новые entries.
4. Меняются ли сумма, postings, metadata, дата, payee/narration, tags/links.
5. Какую правило вывода зарегистрировать.
6. Разбирается ли итоговый автономный файл в RustLedger без ошибок и без двойного учёта.

## 6. Минимальный набор политик для первого готового к рабочей среде сборщика

Первый рабочий builder не обязан поддерживать произвольные Python plugins. Он обязан поддерживать точный набор plugins реальной рабочей книги на зафиксированных версиях зависимостей.

Для готовности нужны:

- policy tests для всех plugins, реально присутствующих в root production configuration;
- отказ при встрече неизвестного plugin либо неподдерживаемого режима его конфигурации;
- фиксация версий зависимостей плагинов в образе и CI fixture;
- контейнерная проверка через RustLedger на ledger, который проходит через тот же набор plugins и содержит rounded FX `@@`.

## 7. Решение по ошибкам и расширению поддержки

Если впоследствии пользователь добавит новый плагин или изменит конфигурацию так, что действующее правило неприменима, сервер должен вернуть управляемую ошибку формирования снимка с указанием неподдерживаемого плагина или его режима. Нельзя автоматически переходить к повторной печати всего материализованной книги: такой запасной режим вновь допускает тихую порчу бухгалтерского смысла.
